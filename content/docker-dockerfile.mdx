![docker](/docker_logo.png 'docker')

Docker 是一个用于构建和运行容器化应用的平台。容器会将源代码、依赖和运行环境打包成可重复使用的单元，让应用可以运行在笔记本电脑、服务器或 Kubernetes 集群等不同环境中。

启动容器之前，需要先准备容器镜像。镜像定义了容器文件系统的初始状态，而 [Dockerfile](https://docs.docker.com/reference/dockerfile) 则通过一系列指令描述如何构建镜像。

本文将介绍 Dockerfile 的工作方式、常用指令、镜像构建流程，以及编写 Dockerfile 时需要注意的实践。

## 什么是 Dockerfile ？

Dockerfile 是一个文本文件，其中包含 Docker 守护进程构建容器镜像时需要执行的指令。运行 [**docker build**](https://docs.docker.com/reference/cli/docker/image/build) 后，Docker 会按照文件中的顺序处理每一行，并逐步组装镜像。

Dockerfile 的基本语法如下：

```bash
# Comment
INSTRUCTION arguments
```

每条指令都使用一个关键字表示具体操作，例如从工作目录复制文件，或者在镜像中执行命令。

按照惯例，指令通常使用大写字母。Dockerfile 解析器并不[强制要求](https://docs.docker.com/reference/dockerfile)这样书写，但大写可以让指令更容易识别。

当一条指令包含较多参数时，可以使用反斜线将它拆分到多行：

```bash
RUN apt-get install \
curl \
  wget
```

以 **#** 开头的行会被解析为注释。解析器会忽略这些内容，因此你可以使用注释记录 Dockerfile 的用途和说明。

## Dockerfile 常用指令

Docker 支持超过 15 种 Dockerfile 指令，用于向镜像添加内容或设置配置。下面是其中最常用的几种。

**FROM**

```bash
FROM ubuntu:20.04
```

**FROM** 通常是 Dockerfile 的第一条指令。它指定一个现有镜像作为基础，后续指令都会应用在该镜像的文件系统之上。

**COPY**

```bash
COPY main.js /app/main.js
```

**COPY** 用于将文件或目录添加到镜像文件系统。使用该镜像启动的容器，也会包含这些复制进去的文件。

第一个参数是 Docker 主机上的源路径，第二个参数是镜像中的目标路径。添加 **--from** 标志后，还可以直接从另一个 Docker 镜像复制文件：

```bash
# Copies the path /usr/bin/composer from the composer:2 image
COPY --from=composer:2 /usr/bin/composer composer
```

**ADD**

```bash
ADD http://example.com/archive.tar /archive-content
```

**ADD** 的作用与 **COPY** 类似，但它还支持远程文件 URL 和自动解压存档。存档会被解压到容器中的目标路径，并支持 gzip、bzip2 和 xz 格式。

虽然 **ADD** 可以简化部分构建操作，但官方[不鼓励随意使用](https://docs.docker.com/develop/develop-images/dockerfile_best-practices/#add-or-copy)，因为它可能隐藏重要行为。例如，误用 **ADD** 会让存档直接解压到容器，而不是按原样复制。

**RUN**

```bash
RUN apt-get update && apt-get install -y nodejs
```

**RUN** 用于在正在构建的镜像中执行命令。每次执行都会在现有镜像层之上创建一个新的[镜像层](https://docs.docker.com/storage/storagedriver/#images-and-layers)，其中保存命令产生的文件系统变化。

这条指令通常用于安装和配置镜像所需的软件包。

**ENV**

```bash
ENV PATH=$PATH:/app/bin
```

**ENV** 用于设置容器内可用的环境变量。它的写法与 shell 变量赋值类似，通过等号连接变量名和值。

## 编写 Dockerfile 和构建镜像

下面通过一个简单的 Node.js 应用，演示如何创建 Dockerfile 并构建镜像。

首先，新建项目目录，并将以下代码保存为 **main.js**：

```javascript main.js
const { v4: uuid } = require('uuid');

console.log('Hello World');
console.log(`Your ID is ${uuid()}`);
```

然后，使用 npm 将 uuid 软件包添加到项目中：

```bash bash
npm install uuid
```

接下来，将以下指令保存到工作目录中的 **Dockerfile**：

```dockerfile Dockerfile
FROM node:16
WORKDIR /app

COPY package.json .
COPY package-lock.json .
RUN npm install

COPY main.js .

ENTRYPOINT ["node"]
CMD ["main.js"]
```

这个 Dockerfile 会按顺序完成以下操作：

- **FROM node:16**：选择 [Node.js 官方镜像](https://hub.docker.com/_/node)作为基础镜像，后续指令都应用在 **node:16** 之上。
- **WORKDIR /app**：将工作目录切换为 **/app**。后续使用相对路径的指令，例如 **COPY**，都会以容器内的 **/app** 为基准。
- **COPY package.json**：接下来的两行会从主机工作目录复制 **package.json** 和 **package-lock.json**。目标路径 **.** 表示文件将以原名保存在容器的工作目录中。
- **RUN npm install**：在容器文件系统中执行 **npm install**，安装项目依赖。
- **COPY main.js**：将应用源代码添加到容器。这一步位于 **RUN** 之后，因为源代码通常比依赖变化得更频繁，这种顺序可以更有效地利用 Docker 的[构建缓存](https://docs.docker.com/build/cache)。
- **ENTRYPOINT \["node"]**：设置镜像的[入口点](https://docs.docker.com/reference/dockerfile/#entrypoint)，使用该镜像创建容器时会自动启动 **node**。
- **CMD \["main.js"]**：为镜像入口点提供默认参数，因此本例会使用 **node** 运行应用代码。

### 构建镜像

现在可以通过 **docker build** 构建镜像。在终端中运行：

```bash bash
docker build -t demo-image:latest .
```

Docker 会依次执行 Dockerfile 中的指令，并将构建过程输出到终端。

**docker build** 接收构建上下文路径作为参数。构建上下文决定了 Dockerfile 可以引用哪些路径，例如 **COPY** 无法访问构建上下文之外的文件。

最常见的做法是将构建上下文设置为 **.**，表示当前工作目录。

Docker 默认读取工作目录中的 Dockerfile。添加 **-f** 标志后，可以指定其他位置的 Dockerfile：

```bash bash
docker build -f dockerfiles/app.dockerfile -t demot-image:latest .
```

**-t** 标志用于设置镜像构建完成后的标签。如果需要添加多个标签，可以重复传入该标志。

### 使用镜像

镜像构建完成后，启动一个容器查看代码的执行结果：

```bash
# !focus(1)
docker run demo-image:latest

Hello World!
Your ID is 606c3a30-e408-4c77-b631-a504559e14a5
```

根据 Dockerfile 中的指令，镜像文件系统已经包含 Node.js 运行时、npm 依赖和应用源代码，因此容器启动后可以直接运行程序。

## Dockerfile 最佳实践

编写 Dockerfile 并不复杂，但一些常见问题会影响镜像的可用性、性能和安全性。下面介绍需要注意的实践。

### 不使用 latest 基础镜像

在 **FROM** 中使用 **node:latest** 等镜像标签存在风险。镜像作者发布新的主要版本后，可能会立即将 **latest** 指向新版本，导致重新构建时意外选择不同版本。

这种变化可能造成构建失败或容器软件无法正常运行。选择 **node:16** 这类明确标签更可预测，只有在没有其他选择时才使用 **latest**。

### 使用可信的基础镜像

**FROM** 引用的基础镜像内容会成为最终镜像的一部分。如果基础镜像被破坏，其中的恶意软件也可能进入容器。

因此，应优先选择 Docker Hub 中标记为[官方或经过验证的发布者](https://hub.docker.com/search?q=&image_filter=official,store)提供的镜像，降低后门和安全问题的风险。

### 使用 HEALTHCHECK 启动容器健康检查

容器进入故障状态时，健康检查可以通知 Docker 和管理员。Docker Swarm、Kubernetes 等编排工具也可以利用这些信息自动重启异常容器。

在 Dockerfile 中添加 [**HEALTHCHECK**](https://docs.docker.com/reference/dockerfile/#healthcheck)，即可设置 Docker 在容器内执行的健康检查命令：

```dockerfile Dockerfile
HEALTHCHECK --timeout=3s \
  CMD curl -f http://localhost || exit 1
```

运行 **docker ps** 查看容器时，输出中会显示容器的健康状态：

```bash
# !focus(1)
docker ps

CONTAINER ID   IMAGE                	COMMAND              CREATED    	STATUS
335889ed4698   demo-image:latest      "httpd-foreground"   2 hours ago	Up 2 hours (healthy)
```

### 正确设置 ENTRYPOINT 和 CMD

**ENTRYPOINT** 和 **CMD** 是[密切相关的指令](https://docs.docker.com/reference/dockerfile/#understand-how-cmd-and-entrypoint-interact)。**ENTRYPOINT** 设置容器启动时运行的进程，**CMD** 则为该进程提供默认参数。

使用 **docker run** 启动容器时，可以通过自定义参数覆盖 **CMD**。在前面的示例中，**ENTRYPOINT \["node"]** 和 **CMD \["main.js"]** 会让 **docker run demo-image:latest** 执行 **node main.js**。

如果运行 **docker run demo-image:latest app.js**，Docker 则会执行 **node app.js**。

### 不要在镜像中硬编码密钥

Dockerfile 不应该包含密码、API 密钥等硬编码密钥。在 Dockerfile 中设置的密钥会进入镜像，并适用于所有使用该镜像的容器，任何能够访问镜像的人都可能查看这些信息。

更安全的方式是在[启动单个容器时](https://docs.docker.com/reference/cli/docker/container/run/#env)设置环境变量，而不是在 Dockerfile 中提供默认值。

### 为镜像添加标签，便于更好的组织

当团队拥有大量镜像时，组织和识别它们会变得困难。使用 **LABEL** 可以为镜像设置任意元数据，例如项目或应用相关的信息。

按照惯例，标签通常采用反向 DNS 语法：

```dockerfile Dockerfile
LABEL com.example.project=api
LABEL com.example.team=backend
```

容器管理工具通常会显示这些标签，并允许按不同值筛选镜像。

### 为镜像设置非 Root 用户

Docker 默认以 root 用户运行容器进程。由于容器中的 root 与主机上的 root 相同，一旦恶意进程突破容器隔离，就可能在 Docker 主机上执行任意命令。

在 Dockerfile 中添加 **USER** 可以设置容器运行时使用的用户和组。为容器指定非 root 用户，有助于降低这类风险：

```dockerfile Dockerfile
# set the user
USER demo-app

# set the user with a UID
USER 1000

# set the user and group
USER demo-app:demo-group
```

### 使用 .dockerignore 避免过长的构建时间

[构建上下文](https://docs.docker.com/build/building/context)是 **docker build** 可以访问的路径集合。执行 **docker build .** 时，当前工作目录会作为构建上下文，其中可能包含不需要的文件和目录。

应从构建上下文中排除 Dockerfile 未使用的路径，以及会由其他指令在容器中重新创建的内容。这样可以减少 Docker 在构建开始时复制的数据，提高构建效率。

在工作目录中添加 **.dockerignore**，即可排除指定文件和目录。它的语法与 [**.gitignore**](https://git-scm.com/docs/gitignore) 类似：

```txt .dockerignore
.env
.local-settings
node_modules/
```

### 保持镜像轻量

过大的 Docker 镜像会降低构建速度，并增加镜像在注册表之间传输的成本。

只安装软件运行所需的最小软件包集合，可以减少镜像体积。选择 [Alpine Linux](https://hub.docker.com/_/alpine)（5MB）等轻量基础镜像，也能避免使用 Ubuntu（28MB）等大型发行版带来的额外体积。

### 检查 Dockerfile 并扫描镜像以检查漏洞

Dockerfile 中的错误可能破坏构建、引发意外行为或违反最佳实践。构建之前，可以使用 [Hadolint](https://github.com/hadolint/hadolint) 等检查工具发现问题。

Hadolint 可以通过自身的镜像运行：

```bash bash
docker run --rm -i hadolint/hadolint < Dockerfile
```

检查结果会直接显示在终端中。

还可以使用 [Trivy](https://github.com/aquasecurity/trivy) 等容器扫描工具检查已构建镜像。它们能够识别镜像文件系统中过期的软件包和已知漏洞，在部署前运行扫描可以避免存在风险的容器进入生产环境。

## 要点

Dockerfile 使用一系列有序指令描述容器镜像的构建过程。它可以从构建上下文复制文件、在镜像文件系统中执行命令，并通过标签等元数据组织镜像。

Dockerfile 并不局限于 Docker。除了约定使用的 Dockerfile 文件名，Podman 等工具也支持更通用的 [Containerfile](https://developers.redhat.com/blog/2019/02/21/podman-and-buildah-for-docker-users)。Dockerfile 指令由[开放容器倡议（OCI）](https://opencontainers.org)镜像规范定义，因此生成的镜像可以运行在任何兼容 OCI 的容器运行时中。
